# 软件 UI 开发

## 确定要做哪一部分

从真实入口找到目标页面、窗口或组件，了解它的用户任务、相邻区域和调用方。检查已有截图、设计稿、组件库、设计变量和同类界面。新项目根据需求识别首要任务和目标平台。把含糊描述落到能看到或操作的细节，例如哪些信息先看见、哪些操作常驻、默认展示什么以及操作后的反馈。

让布局适合区域的用途。设置页按任务分组并给出保存反馈。工作列表和工具面板优先给数据与常用操作留空间。对话框聚焦当前决定，提供清楚的退出方式并处理焦点。可以自行决定可逆的局部间距、对齐或分组。若希望把改动扩展到共享组件、多个页面或主流程，先用样例确认范围。现有界面改版时，尽早取得修改前的截图或操作基线，供同条件复测。

## 调查指定风格

开发者提到具体设计系统、产品或风格名称时，查看官方规范、可访问的产品实例或该风格的可靠原始参考。根据开发者指出的参考图细节，提炼本区域可直接实现的规则，例如行高、间距、字重层级、强调色、边框和选中状态。用这些规则指导样例及最终检查，并附上支持关键选择的来源。外部产品参考用于提炼设计原则，再结合目标产品的内容、组件和平台习惯实现。

## 用短代码对齐关键设计

新页面、显著改版、共享组件或跨页面变更、主流程变化，以及会影响实现的描述歧义，先在回复里做一次设计对齐。在开发者已明确要求直接实现或已确认该设计的情况下，按其指示继续。清楚的小改动直接实现和验证。

1. 用一两句说清对当前区域、用户任务和关键选择的理解。给出一段能体现选择的最小组件代码，优先使用项目的语言、现有组件和设计变量。有条件就附可运行预览及打开方式，把探索保留在独立样例中。
2. 问一个会改变实现的具体问题，并等待反馈后集成。例如「你说的紧凑，主要想减少行高，还是想让更多信息同时可见？」
3. 收到反馈后，先在回复中给出修订后的关键代码，条件允许时同步更新预览。按反馈更新可观察的验收条件。反馈足以定方向时，同一轮落实到实际入口与生产组件。仍有实质分歧时，给出受影响的修订片段并聚焦这一点提问。

例如，搜索结果页要确认高级筛选的默认展开状态时，可以展示如下片段。

```html
<details>
  <summary>更多筛选</summary>
  <label><input type="checkbox" name="recent" /> 仅看最近 7 天更新</label>
</details>
```

> 常用筛选一直可见。高级筛选应默认收起，还是进入结果页就展开？

## 用项目技术栈实现

从依赖清单、锁文件、同类组件和应用入口确认实际语言、框架版本、样式系统、状态归属及运行方式。遇到不熟悉的 API，查对应版本的官方文档，再用类型检查、构建或最小运行例验证用法。沿用现有组件接口、设计变量、状态管理和交互习惯。

- **Web** 使用 Flexbox 或 Grid 表达布局，优先使用语义化 HTML 和原生控件，沿用项目断点。用框架原有的数据流渲染状态，检查 CSS 溢出、长文本、焦点和键盘操作。新增框架组件时，沿项目现成写法安排事件、派生状态和副作用。
- **桌面软件**使用原工具包的布局、菜单、对话框和快捷键，检查窗口缩放、DPI、最小尺寸与键盘导航。
- **移动 App** 使用平台或项目原有的导航、触控组件和安全区处理。检查软键盘遮挡、触控目标与返回行为。

将样例里确认的设计接入真实数据、事件和路由。随任务检查加载、空数据、错误、禁用和成功反馈等适用状态。自定义控件保留正确语义及焦点行为。布局调整用目标窗口尺寸和代表性的长文本跑一遍。

## 按需使用可商用素材

需要图片或纹理时，先查看项目素材。缺少合适素材再按用途、尺寸和裁切需求搜索。到原始素材页和适用许可页核实能否免费商用、所需修改及随软件分发，并核对署名条件和实际用法涉及的肖像或商标条款。选择授权覆盖该用途的素材。证据不足时先用已授权的候选或占位。

小纹理和背景在授权明确后可直接使用。决定视觉方向的主图随样例一起确认。把原始素材页、作者、许可链接、核查日期和必要署名记到项目惯用的位置。按显示尺寸导出，并在实际界面检查裁切、加载和文字覆盖效果。

## 自查并对比上一版

完成后从真实入口执行同一任务，尽可能用相同数据、状态、窗口尺寸及主题对照上一版。保存可复查的截图或操作结果。有基准的改版逐项说明实际差异。首次开发按用户任务和验收条件检查。基准或运行环境不可用时，写明缺少哪项证据。

| 维度 | 观察点 |
| --- | --- |
| 易辨性 | 内容层级、文字可读性、主操作能否找到、控件状态是否可区分，以及键盘焦点是否可见。 |
| 美观性 | 对齐、间距、字重与色彩是否协调，是否符合已确认的风格，并与周边界面衔接。 |
| 简洁性 | 界面元素是否服务于任务，是否减少重复信息或多余步骤，常用操作和必要反馈是否仍容易找到。 |

发现主操作难找、文字难读、关键状态难辨或交互退化时，先修复再复测。出现影响方向的审美取舍时，提供前后预览和具体差异供开发者选择。运行与修改相关的构建、类型检查或测试。交付时报告关键差异、实际通过的检查和仍未验证的部分。

## 按需调用工程技能

从当前可用技能中按问题选择。需要可操作的可丢弃样品来验证较大的设计选择时用 `prototype`。开发者要求逐层拷问时用 `grilling`。需要诊断可复现的 UI 故障时用 `diagnosing-bugs`。要求按规范和规格审查变更时用 `code-review`，仍按上节做视觉和操作验证。读取选中的 `SKILL.md`，在当前任务范围内使用。技能不可用时按本流程继续。[Skills for Real Engineers](https://github.com/mattpocock/skills#reference)
